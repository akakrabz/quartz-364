> [!abstract] In one breath
> To compare training runs you need their curves side by side, while they train and afterwards. **TensorBoard** does this with two lines of code: create a [`SummaryWriter`](https://docs.pytorch.org/docs/stable/tensorboard.html) pointing at a folder for this run, and call `writer.add_scalar(tag, value, step)` wherever you would have printed a number. Each run writes an event file into its own sub-folder; `tensorboard --logdir=logs` serves an interactive page that overlays every run in `logs/`. The lecture uses it to compare six Transformer runs and reads off a design decision.

## What it is

Until now the course looked at training through `tqdm` progress bars, `print` statements, and Matplotlib plots drawn after training finished. That has two limits: nothing can be seen **during** a long run, and comparing several runs means saving results and writing plotting code by hand.

A logging tool fixes both. The lecture names the ones common in industry (Weights & Biases, MLflow, Neptune) and picks TensorBoard because it is lightweight and needs no account. TensorBoard was written for TensorFlow, a competing framework, but PyTorch can write its log format through [`torch.utils.tensorboard`](https://docs.pytorch.org/docs/stable/tensorboard.html). It usually needs installing: `pip install tensorboard`.

The moving parts:

| Piece | What it is |
| --- | --- |
| **log directory** (`logs/`) | one folder holding a sub-folder per training run |
| **run folder** (`logs/demb_128_nlayers_1_nhead_4_dropout_00/`) | written by one `SummaryWriter`; contains an `events.out.tfevents…` file |
| **scalar** | one logged number: a `tag` (its name), a value, and a `global_step` (its x-coordinate) |
| **TensorBoard server** | a local web page (default `http://localhost:6006/`) that reads the log directory and plots every run |

## What you should know

- `writer = SummaryWriter(run_dir)`: one writer and one folder **per run**.
- `writer.add_scalar(tag, scalar_value, global_step)` logs one point. Call it once per epoch (or per logging step) for each quantity.
- A `/` in the tag groups plots: `'BLEU Scores/Train BLEU'` and `'BLEU Scores/Validation BLEU'` become two cards under one "BLEU Scores" section.
- Launch with `tensorboard --logdir=logs` from a terminal, then open the printed local URL.
- Name run folders from the hyperparameters with a format string, and refuse to overwrite an existing folder.
- View losses on a **log** y-axis. Smoothing is an exponential moving average for display only.
- The lecture's conclusion from its six runs: increasing the embedding dimension keeps helping; the number of attention heads makes no difference to validation BLEU.

## From the lecture

*From the class recording, paraphrased.*

- Progress bars and print statements are a "very crude" way to watch training: nothing visual during the run, and tracking several runs gets awkward.
- In industry other tools are more popular. TensorBoard is used here because nobody has to create an account, and for this course it is "more than enough".
- Keep one overall directory with a sub-folder per run. Do not name runs "experiment one, experiment two": encode the settings in the folder name so you can tell later what each run was.
- Raise an exception if the folder already exists. Two event files in one folder mix two runs into one garbled plot.
- Set learning-rate milestones **relative** to the number of epochs (70% and 85%), so the schedule scales when you change the training length.
- Look at the loss on a log scale, since it spans several orders of magnitude; there is no benefit to a log scale for BLEU or accuracy.
- The run filter takes a regular expression. Filtering on `nhead_4` shows the embedding sweep alone; filtering on `demb_128` shows the heads sweep alone. That is how to read an ablation study.
- On the shared campus notebooks (ICRN) live monitoring may not be reachable. The fallback is fine: train, download the `logs` folder, and run TensorBoard on your own machine.
- Watching curves update live can catch a doomed run early, but he advised against staring at it: hanging on every 30-second refresh is "not good for your health".
- For the final project: also save model checkpoints every few epochs or at the best validation score, because the campus GPUs guarantee about 24 hours and a run can be cut off ([[4-pytorch-training/underfitting-and-overfitting#saving-the-best-model|saving the best model]]).

## Logging in three steps

```python
from torch.utils.tensorboard import SummaryWriter

writer = SummaryWriter(full_log_path)                       # 1. one writer per run

for i in range(n_epochs):
    ...                                                     # train one epoch
    writer.add_scalar('Loss', epoch_loss/len(train_loader), i+1)          # 2. log scalars
    writer.add_scalar('BLEU Scores/Train BLEU', train_bleu, i+1)
    writer.add_scalar('BLEU Scores/Validation BLEU', val_bleu, i+1)
```

```
tensorboard --logdir=logs          # 3. in a terminal; then open http://localhost:6006/
```

The third argument is the x-coordinate. The lecture passes `i+1`, the number of completed epochs, so every curve is plotted against epochs. Besides scalars a writer can log histograms (`add_histogram`), images (`add_image`), Matplotlib figures (`add_figure`), text, audio and more; the lecturer's example was publishing a segmentation model's predicted masks at several points in training.

## Naming runs

```python
log_dir = 'demb_{}_nlayers_{}_nhead_{}_dropout_{:02d}'.format(d_emb, n_layers, n_head,
                                                              int(dropout*100))
full_log_path = os.path.join('logs', log_dir)
if not os.path.exists(full_log_path):
    os.mkdir(full_log_path)
else:
    raise Exception('Make sure this directory is empty and you are not overwriting existing results!')

writer = SummaryWriter(full_log_path)
```

With `d_emb = 128`, `n_layers = 1`, `n_head = 4`, `dropout = 0.0` the folder is `demb_128_nlayers_1_nhead_4_dropout_00`: the `{:02d}` prints the dropout percentage with two digits. The name is the run's documentation, and it is what the filter box in TensorBoard matches against.

## The updated training loop

Lecture 22's `detailed_transformer_train` is the [[7-transformers/pytorch-transformer-layers#training-it|Lecture 21 loop]] with a scheduler and a writer added. The new lines are marked:

```python
def detailed_transformer_train(transformer, dataset, train_dataset, val_dataset, train_loader,
                               n_epochs, optimizer, scheduler, writer, device='cpu'):
    criterion = nn.CrossEntropyLoss()
    all_losses, train_accs, val_accs = [], [], []
    log_freq = max(n_epochs // 100, 1)            # at most 100 evaluations
    for i in tqdm(range(n_epochs)):
        epoch_loss = 0
        for batch in train_loader:
            optimizer.zero_grad()
            curr_loss = 0
            for j in range(len(batch)):           # one sentence at a time
                english, french, english_tensor, french_tensor = batch[j]
                english_tensor = english_tensor.to(device)
                french_tensor = french_tensor.to(device)
                predictions = transformer(english_tensor, french_tensor)
                example_loss = criterion(predictions, french_tensor.squeeze(1))/len(batch)
                curr_loss += example_loss
            curr_loss.backward()
            optimizer.step()
            epoch_loss += curr_loss.item()
        all_losses.append(epoch_loss/len(train_loader))
        writer.add_scalar('Loss', epoch_loss/len(train_loader), i+1)     # NEW
        scheduler.step()                                                 # NEW: once per epoch

        if (i+1) % log_freq == 0:
            train_bleu = evaluate_transformer(transformer, train_dataset, dataset, device)
            val_bleu = evaluate_transformer(transformer, val_dataset, dataset, device)
            writer.add_scalar('BLEU Scores/Train BLEU', train_bleu, i+1)         # NEW
            writer.add_scalar('BLEU Scores/Validation BLEU', val_bleu, i+1)      # NEW
            train_accs.append(train_bleu)
            val_accs.append(val_bleu)
    return transformer, all_losses, train_accs, val_accs
```

The set-up around it:

```python
lr = 1e-2
n_epochs = 100
optimizer = torch.optim.SGD(transformer_model.parameters(), lr=lr, momentum=0.99)
scheduler = torch.optim.lr_scheduler.MultiStepLR(optimizer,
                                                 milestones=[int(n_epochs*0.7), int(n_epochs*0.85)],
                                                 gamma=0.1)
```

`evaluate_transformer` translates 1,000 randomly chosen sentences greedily and averages their [[7-transformers/sequence-to-sequence-rnns#bleu-scoring-a-translation|BLEU scores]], so each logged BLEU point carries some sampling noise. The scheduler is explained on the [[4-pytorch-training/learning-rate-schedulers#multisteplr-in-lecture-22|learning-rate schedulers]] page. The data split is fixed with `np.random.seed(0)`, so all runs train and validate on the same sentences.

## Using the TensorBoard page

What the lecture demonstrated in the browser:

- **Runs** are listed on the left with a colour each; colours can be changed (useful for colour-vision deficiencies, or to mark a reference run).
- **Sections and cards.** `Loss` is one card; the `BLEU Scores/…` tags share a section with two cards.
- **Hover** shows, for each run, the raw value, the smoothed value, the step, the wall-clock time and the time since the run started, which tells you which runs were slow.
- **Smoothing** (a slider, 0 to 1) draws an exponential moving average over the raw points, shown faintly behind. Use it to see the trend in a noisy metric; set it to 0 to see the logged numbers.
- **Log y-axis** for the loss. On a linear axis the last 80 epochs of a loss that fell from 4.4 to 0.04 are a flat line.
- **Filter runs** with a regular expression on the folder name.
- **Live updates.** A run in progress appears as soon as its first point is written, and the page reloads periodically.

More heads make the model fit the training set faster early on, but the validation curves cannot be told apart at the end, and the parameter count is identical ([[7-transformers/multi-head-attention#same-cost-as-one-head|heads split the same matrices]]). The lecturer's conclusion: stop fiddling with the number of heads, leave it at a standard value such as 4, and spend the effort on settings that matter. This matches what the course saw before: [[7-transformers/multi-head-attention#do-more-heads-help|multi-head attention helps less than the other ingredients]].

This is an **ablation study**: one baseline (`d_emb` = 128, 4 heads), and each other run changes one setting. Homework 6 asked for the same thing on text classification.

> [!note] One run per setting
> Each configuration was trained once, and each BLEU point averages 1,000 random sentences. Differences of one or two hundredths (such as 0.52 against 0.51) are within that noise; differences of 0.05 and more between embedding sizes are not.

> [!trap] Common mistakes
> - **One folder for several runs.** The event files are merged into one zig-zag curve. One run, one folder.
> - **Pointing `--logdir` at a single run folder** when you wanted to compare: point it at the parent (`logs`).
> - **A typo in the command.** The notebook's text has `tensorboard --logdir==logs` with a doubled `=`; the option is `--logdir=logs` (or `--logdir logs`).
> - **Logging a tensor that still holds the graph.** Pass a Python number: `loss.item()`, as the loop does with `curr_loss.item()`.
> - **Different x-axes for different quantities.** If the loss is logged per batch and accuracy per epoch, pass a consistent `global_step` or the curves will not line up.
> - **Reading smoothed values as data.** Smoothing lags behind sudden changes such as the jump after a learning-rate drop.
