> [!abstract] In one breath
> A model is only useful on **new** data, and it can look nearly perfect on the data it was trained on. So the dataset is cut into three **disjoint** parts: the **training set** produces the gradients; the **validation set** is used to choose hyperparameters (learning rate, epochs, weight decay, model size); the **test set** is used once, at the end, to report how well the model generalizes. Training error going down while validation error goes up is overfitting.

## What it is

For a dataset $\mathcal{D} = \{(x_i, y_i)\}_{i=1}^N$ (Lecture 11):

- **Training set** $\mathcal{D}_{\text{train}}$ — the data the model is trained on: its loss is what `loss.backward()` differentiates.
- **Validation set** $\mathcal{D}_{\text{val}}$ — the model does **not** train on it, but we look at its performance to tune **hyperparameters**: learning rate, how long to train, weight decay, momentum, batch size, number of layers and their widths, the polynomial degree, $\lambda$.
- **Test set** $\mathcal{D}_{\text{test}}$ — the model does not train on it **and** we do not use it to change anything. It is the final, honest estimate of generalization and the number used to compare models.

The three are disjoint. A usual choice keeps at least half for training and splits the rest roughly equally: the lecture uses **60 : 20 : 20**.

## What you should know

- Definitions and roles of the three sets, and that they share no examples.
- **Parameters** ($w$, $b$, layer weights) are learned by gradient descent on the training set; **hyperparameters** (anything you set by hand) are chosen by comparing validation performance.
- Why the validation number is not the final answer: after you have picked the best of many settings on it, it is optimistically biased. The test set fixes that only if it is used once.
- Reading curves: train ↓ and val ↓ → keep training; train ↓ but val flat or ↑ → **overfitting**; both high → **underfitting** (model too simple or not trained enough).
- Remedies for overfitting: more data, [[5-deep-networks/data-augmentation|augmentation]], [[3-linear-models/ridge-regression|$L_2$ penalty]] / [[4-pytorch-training/optimizers#weight-decay|weight decay]], [[5-deep-networks/dropout|dropout]], a smaller model, stopping at the best validation epoch.

## How to split, in code

Shuffle the indices **once**, then cut the permutation into consecutive pieces — guaranteed disjoint:

```python
indices = np.arange(len(dataset))
np.random.shuffle(indices)
train_idx = indices[:N_train]
val_idx = indices[N_train:N_train+N_val]
test_idx = indices[N_train+N_val:]
```

then build one loader per piece with `SubsetRandomSampler` (or use `random_split`) — see [[4-pytorch-training/datasets-and-dataloaders#dataloaders-and-the-train--val--test-split|DataLoaders]]. Datasets such as Fashion-MNIST come with a fixed train/test split (60,000 / 10,000); carve the validation set out of the training part. (Lecture 11's Fashion-MNIST demo takes a shortcut and uses the official `train=False` split as its validation loader, so it has no separate test set.)

## Leaks: how a test score becomes meaningless

- Tuning any hyperparameter on the test set (including "train a few versions and keep the one with the best test score").
- Overlapping splits — duplicates or the same example drawn into two sets.
- Preprocessing fitted on all the data (e.g. a normalization mean computed over train + test); fit it on the training set only.
- Reporting training accuracy as if it measured generalization.

> [!trap] Common mistakes
> - Calling the validation set "test" and reporting the best validation score as final.
> - Computing gradients or calling `optimizer.step()` on validation batches: that is training on them. Evaluate under `torch.no_grad()`.
> - Concluding a model is good because training accuracy is ~100%: with enough parameters almost any model reaches that.
> - Dividing validation accuracy by the number of *batches* instead of the number of examples.
